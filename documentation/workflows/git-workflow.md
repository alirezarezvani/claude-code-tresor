# Branching Strategy

**Workflow**: Trunk-based (PRs → `main`)

## Overview

Claude Code Tresor uses trunk-based development. There is **one long-lived branch**: `main`. All work happens in short-lived branches that open a pull request against `main` and merge once CI is green.

Releases are automated by [release-please](https://github.com/googleapis/release-please): every merge to `main` updates a release PR with a CHANGELOG entry; merging that PR cuts a tag and a GitHub Release.

## Branch naming

CI enforces this pattern:

```
^(feat|fix|docs|chore|refactor|test|build|ci|perf|style|hotfix|release|claude|dependabot|renovate)/[a-z0-9][a-z0-9._/-]*$
```

Examples:

- `feat/orchestration-command-rollback`
- `fix/install-backup-recursion`
- `docs/update-faq`
- `ci/trunk-based-cleanup`
- `claude/<auto-generated-slug>` — for Claude Code AI sessions
- `dependabot/...`, `renovate/...` — automation

## Commit messages

[Conventional Commits](https://www.conventionalcommits.org/) — release-please uses these to decide version bumps:

| Type           | Bump  | Example                                            |
| -------------- | ----- | -------------------------------------------------- |
| `fix:`         | patch | `fix: stop install.sh from recursing into backup`  |
| `feat:`        | minor | `feat: add code-health command`                    |
| `feat!:` / `BREAKING CHANGE:` | major | `feat!: rename @core agents` |
| `docs:` / `chore:` / `test:` / `ci:` / `refactor:` | none | n/a |

Scopes optional but encouraged: `fix(install): ...`, `docs(skills): ...`.

## Workflow

```bash
# 1. Branch from main
git checkout main && git pull
git checkout -b feat/my-thing

# 2. Commit (conventional)
git commit -m "feat(skills): add code-coverage skill"

# 3. Push and open a PR
git push -u origin feat/my-thing
gh pr create --base main
```

CI runs `validate` on every PR: branch name, commit messages, frontmatter schemas, cross-references, doc-count drift, shellcheck, install smoke test, internal markdown links.

Merge once green. release-please opens or updates the release PR automatically.

## Releases

You do nothing manually. release-please watches `main` and maintains a single open PR titled `chore(main): release X.Y.Z`. That PR contains:

- The next version (calculated from conventional-commit history)
- A CHANGELOG.md update
- An updated `version.txt` and `.release-please-manifest.json`

Merge the release PR to cut the tag and GitHub Release.

## Emergency stop

Set `.github/WORKFLOW_KILLSWITCH` to:

```
STATUS: DISABLED
```

CI and release workflows will short-circuit until you flip it back.

## Migration from Git Flow

The repo previously used `dev → main` Git Flow. The `dev` branch is being retired. If you have an open PR against `dev`, retarget it to `main`.
